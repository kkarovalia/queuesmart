QueueSmart Assignment 2 Report

This section covers the User Access and History portion of the front end, which includes the features/auth, features/user-dashboard, and features/history folders. The work here includes the login screen, the registration screen, client side validation on both forms, the user dashboard overview, the active services summary shown on that dashboard, and the reservation and waitlist history screen. The login screen and registration screen both collect the required information and validate them before allowing the user through. Email is checked for a basic valid format and is required, and password is required with a minimum length. The registration screen also checks that the confirm password field matches and that a full name was entered. If any field fails validation, an error message appears under that specific field and the form will not submit until it is fixed. Right now these screens use mock authentication, meaning a successful login or registration simply moves the user to the dashboard rather than checking against a real account, since there is no backend yet for this assignment.

The user dashboard shows an overview of the current queue the user is in, including which service, their position, party size, and estimated wait time. Below that is a table of the active services available to join, showing whether each one is open or closed and its estimated wait. Below that is a summary of recent notifications with a count of unread ones. All of this data currently comes from mock data rather than a real backend. The history screen lists past queues the user has joined, showing the date, service name, party size, wait time, and outcome for each one. There is also a filter so the list can be narrowed down by outcome, such as seated, cancelled, or no show.

Since Assignment 1 was a proposal with no code to test, the biggest change in approach for this assignment was realizing that a build passing without errors does not mean the app actually works. Early on, the app compiled and built successfully but showed a blank white page when opened in a browser, caused by a missing piece in the router setup that the build tools had no way of catching. This was only found by actually opening the app and testing it, not by trusting a clean build. The same thing happened with the layout on smaller screens, which I did through devtools in Firefox. It looked fine on desktop but broke on a phone sized screen until it was tested directly at that width. Going forward, the plan is to always check a screen in an actual browser, and at a mobile width, before considering it finished, rather than relying on the build finishing cleanly. I did not have time to test it on a proper phone screen, but since it worked on the devtools, I am hoping it does so on a mobile browser as well.

As none of the shared setup existed yet when this work started, such as the folder structure, the shared types, the mock data, the page routing, and the overall layout with the navigation bar, that had to be built first so that the auth, dashboard, and history screens had somewhere to live and so the rest of the team would have working navigation and placeholders for their screens once this was pushed. A few existing issues in the shared project files were also found and fixed along the way, including a missing dependency in package.json, but it should be entirely sorted now.

The technologies used are React with TypeScript, Vite as the build tool, TanStack Router for page navigation, and TanStack Query for handling the mock data in a way that will be easy to swap for a real backend later. Plain CSS with shared color and spacing variables is used across the app so that every screen looks consistent, and this also means dark mode works automatically based on the user's system settings.
